# VaxInsight Supervisor Decision Register

## Purpose and Status

This register identifies decisions that must be confirmed before implementation proceeds beyond the current authentication, administrator, and neutral owner-scoped narrative foundation. It does not make those decisions on behalf of the supervisor, project owner, public-health authority, data custodian, or ethics authority.

The repository contains a FastAPI backend, an Expo mobile client, a provisional vaccine-information and question/reviewer workflow, and the account-management implementation. The referenced Secure AI Labs 60-day plan, research proposal, supervisor requirements, dataset, dataset assessment, ethics approval, and approved public-health source list are still missing. The mobile implementation is evidence of a technical choice, not confirmation that the supervisor or ethics authority approved the product scope. Each decision below records that evidence limitation.

**Status values:** `Unresolved` means no authoritative decision was found. `Confirmed` should be used only after a named approver records the decision and its evidence. All decisions in this initial register are unresolved.

### Provisional Review-Workflow Decisions

The following implementation choices were approved provisionally during the
review-workflow architecture discussion. They are recorded separately from the
formal register because no named supervisor or ethics approver is present in the
repository. They must not be treated as production or ethics confirmation.

| ID | Provisional decision | Implementation boundary | Status |
|---|---|---|---|
| RV-001 | Administrators with `narrative.assign` manage assignments. | Assignment management is separate from unrestricted narrative-content access. | Provisional |
| RV-002 | Eligible reviewers must be active accounts with the `reviewer` role. | Suspended, deactivated, deleted, or differently-roled accounts cannot receive or use assignments. | Provisional |
| RV-003 | A narrative has at most one active reviewer assignment. | Reassignment revokes the old assignment and creates a new pending assignment. | Provisional |
| RV-004 | Review outcomes are `needs_further_review`, `evidence_supports_claim`, `evidence_does_not_support_claim`, and `insufficient_evidence`. | Outcomes are structured human-review records, not verified medical truth. | Provisional |
| RV-005 | Review status is separate from narrative submission status. | The initial workflow uses `pending`, `in_review`, `reviewed`, and `requires_escalation`. | Provisional |
| RV-006 | Assignment and review history is visible to the active assigned reviewer and authorized assignment managers. | Narrative owners do not receive internal review notes through this workflow. | Provisional |
| RV-007 | Reassignment and revocation require a reason and preserve prior records. | Assignment rows and review rows are not deleted by the API. | Provisional |
| RV-008 | Escalation requires an explicit authorized human decision. | No automatic escalation resolution is implemented. | Provisional |

## Decisions That Directly Block Further Implementation

The following decisions prevent responsible implementation of the corresponding areas:

- SD-001 to SD-005 block final user journeys, narrative permissions, submission, review, and approval workflows.
- SD-006 and SD-007 block dataset assessment, target selection, model development, inference, and XAI implementation.
- SD-008 blocks research language/model commitments and validated Kinyarwanda outputs.
- SD-009 blocks population of the content store with approved health information and production communication claims.
- SD-010 blocks any LLM assistant scope.
- SD-011 blocks administrator access to research resources.
- SD-012 and SD-015 block data collection, secondary use, retention, deletion, and operational deployment where ethics or policy approval is required.
- SD-013 blocks official framework approval and Android compatibility claims, although a provisional Expo/React Native implementation exists.
- SD-014 and SD-016 block release claims about usefulness, safety, explanation quality, and human oversight.

## Confirmation Record

When a decision is made, update the relevant row with the date, approver name/role, evidence or meeting record, selected option, constraints, and affected requirement IDs. A decision should not be marked `Confirmed` based only on an implementation convenience or a dependency already present in `requirements.txt`.
